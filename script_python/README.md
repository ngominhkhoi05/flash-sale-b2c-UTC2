# script_python/

Python data-generation scripts for the B2B Procure backend.

## Purpose

Generate large seed datasets as CSV files that can be bulk-imported into
the PostgreSQL database. The current target is:

- **1,000,000** rows in `products`
- **2,000,000** rows in `product_prices` (2 price tiers per product, ~1M each)

The schema in `products` / `product_prices` is owned by the Java
backend (`db/migration/V1__init_schema.sql`). The CSV column layout of
this generator matches that schema exactly.

## Layout

```
script_python/
├── README.md
├── requirements.txt
├── generate_products.py     # legacy: 1M products + 2M prices for b2b-procure
├── generate_all_seeds.py    # current: 16 seed CSVs for flash-sale-b2c (~1,133 rows)
└── activate_and_run.ps1     # convenience: create venv, install deps, run
```

## Usage

The repository convention is to do all work inside a Python virtual
environment. This folder ships **only the source code**, never an
activated environment. From PowerShell:

```powershell
cd D:\b2b-procure-system\b2b-procure-system\script_python
.\activate_and_run.ps1
```

`activate_and_run.ps1` will:

1. Create `.venv/` inside `script_python/` (if missing).
2. Upgrade `pip`.
3. Install packages from `requirements.txt`.
4. Activate the venv and run `generate_products.py`.

Outputs (in `script_python/`, not committed):

- `products.csv`
- `product_prices_tier1.csv`  (tier 1: quantity 1..10, base price)
- `product_prices_tier2.csv`  (tier 2: quantity 11+, 10% discount)

The price data is split into two files because one CSV with 2M rows is
uncomfortable to open on Windows (Notepad/Excel refuse files that big).
Splitting by tier yields two ~1M-row files that are easy to inspect with
standard tools. Both files share the same schema; the `id` column is
globally unique (tier1 uses the natural id, tier2 uses `id + 1,000,000`)
so they can be loaded into the same `product_prices` table in any order.

## Importing the CSV into PostgreSQL

After the script finishes, use `\copy` (fastest path). Load `products`
first (FK reference), then the two price files in any order:

```sql
\copy products(id, supplier_company_id, category_id, sku, name, description, image_url, stock_quantity, reserved_quantity, status, created_at, updated_at)
  FROM 'products.csv' WITH (FORMAT csv, HEADER true);

\copy product_prices(id, product_id, min_quantity, max_quantity, unit_price, created_at, updated_at)
  FROM 'product_prices_tier1.csv' WITH (FORMAT csv, HEADER true);

\copy product_prices(id, product_id, min_quantity, max_quantity, unit_price, created_at, updated_at)
  FROM 'product_prices_tier2.csv' WITH (FORMAT csv, HEADER true);
```

To speed things up significantly, disable trigger/FK checks during the
bulk load (re-enable immediately after):

```sql
SET session_replication_role = replica;
-- ... run the three \copy commands ...
SET session_replication_role = origin;
```

Note: if you have already inserted other rows, adjust the `id` columns
or use `BIGINT GENERATED BY DEFAULT AS IDENTITY` (set via the
`id_sequence` nextval before import).

## Schema references

The CSV column order matches the result of running these migrations in order:

- `V1__init_schema.sql` — base columns of `products` and `product_prices`
- `V7__add_reserved_quantity_to_products.sql` — adds `reserved_quantity`
  (`INT NOT NULL DEFAULT 0`) to `products`, placed between
  `stock_quantity` and `status`
- `V11__normalize_checkout_foundation.sql` — enforces:
    - `products.stock_quantity >= 0`
    - `products.stock_quantity >= reserved_quantity`

`reserved_quantity` is always emitted as `0` by this generator; it is
managed at runtime by the reservation/lock logic, not by seed data.

## Why CSV and not direct INSERT?

- CSV generation is deterministic, restartable, and reviewable in Git
  diffs of the script (the rows themselves are not committed).
- `\copy` streams directly into Postgres without ORM overhead, which
  keeps the 1M-row insert under minutes on a local Docker container.
- The Java backend stays untouched; this is a one-shot data-loading
  utility, not part of the application runtime.

### Usage

```powershell
cd D:\flash-sale-b2c-UTC2\script_python
.\activate_and_run.ps1
```

Or directly:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python generate_all_seeds.py
python generate_all_seeds.py --out D:\tmp\seed_csv  # custom output dir
python generate_all_seeds.py --seed 2026            # deterministic seed
```

The script writes 16 CSVs into the output directory (default: this script's
folder). Output files match `*.csv` in `.gitignore` and are NEVER committed.

**If a target CSV already exists, it is deleted first** and re-created
from scratch. This guarantees the file always reflects the current run
(no leftover rows from a previous run with different `--seed` or
parameters). The script prints `(overwriting existing <name>)` to
stderr for each file it replaces.

### Loading into PostgreSQL

The 16 CSVs must be loaded in FK-dependency order. See
`docs/database-seed-data.md` section 6 for the full sequence. Quick reference:

```sql
-- Group A (RBAC + lookup): no FK between them, any order
\copy roles              FROM 'roles.csv'              WITH (FORMAT csv, HEADER true);
\copy permission_groups  FROM 'permission_groups.csv'  WITH (FORMAT csv, HEADER true);
\copy permissions        FROM 'permissions.csv'        WITH (FORMAT csv, HEADER true);
\copy group_permissions  FROM 'group_permissions.csv'  WITH (FORMAT csv, HEADER true);
\copy categories         FROM 'categories.csv'         WITH (FORMAT csv, HEADER true);
\copy banners            FROM 'banners.csv'            WITH (FORMAT csv, HEADER true);

-- Group B (demo, depends on Group A)
\copy users              FROM 'users.csv'              WITH (FORMAT csv, HEADER true);
\copy user_roles         FROM 'user_roles.csv'         WITH (FORMAT csv, HEADER true);
\copy stores             FROM 'stores.csv'             WITH (FORMAT csv, HEADER true);
\copy addresses          FROM 'addresses.csv'          WITH (FORMAT csv, HEADER true);
\copy products           FROM 'products.csv'           WITH (FORMAT csv, HEADER true);
\copy product_variants   FROM 'product_variants.csv'   WITH (FORMAT csv, HEADER true);
\copy flash_sale_slots   FROM 'flash_sale_slots.csv'   WITH (FORMAT csv, HEADER true);
\copy flash_sale_items   FROM 'flash_sale_items.csv'   WITH (FORMAT csv, HEADER true);
\copy vouchers           FROM 'vouchers.csv'           WITH (FORMAT csv, HEADER true);

-- Group C (auto-generated; seed only for demo data)
\copy carts              FROM 'carts.csv'              WITH (FORMAT csv, HEADER true);
\copy store_followers    FROM 'store_followers.csv'    WITH (FORMAT csv, HEADER true);
```

### `images.csv` (V3 polymorphic image table)

`images` is a polymorphic table (one row per image, with `owner_type` and
`owner_id` columns). The seed emits **exactly 1 ACTIVE image per owner** to
satisfy the V3 partial-unique-indexes:

- 1 avatar per `users` (30 rows)
- 1 logo per `stores` (10 rows)
- 1 primary image per `products` (200 rows, `is_primary = true`)
- 1 primary image per `product_variants` (~520 rows, `is_primary = true`)
- ~50% of `product_reviews` get 1 image (~43 rows)

To link a product to its primary image at query time:

```sql
SELECT p.*, i.url AS primary_image_url
FROM products p
LEFT JOIN images i
  ON i.owner_type = 'PRODUCT' AND i.owner_id = p.id AND i.is_primary = true;
```

Products and variants do NOT have a foreign-key column to `images`; the
relationship is resolved by join. The same pattern applies to USER, STORE,
and REVIEW images.

`images.csv` must be loaded AFTER the tables it references (users, stores,
products, product_variants, product_reviews) so `owner_id` values resolve.
The polymorphic FK is logical (V3 has no physical FK), so loading it out
of order will NOT fail the COPY, but you'll get dangling `owner_id`s
that produce no image in the app.

### Important caveats

- `users.password_hash` is a **placeholder** (`$2a$10$placeholder.bcrypt.hash.<role><id>`)
  - replace with real BCrypt hashes before exposing to a real environment.
- `product_reviews.order_item_id` is a placeholder pointing to the review's own
  id; the real V1 schema has `order_item_id BIGINT NOT NULL UNIQUE REFERENCES
  order_items(id)`. Use the application (not seed) to create real review rows
  tied to real order items, otherwise you will get a FK violation on load.
- `products.slug` and `categories.slug` are intentionally left NULL in the
  CSV; V8 / V9 backfill them automatically (idempotent, ASCII-safe regex).
- `is_active` for permissions is emitted as Python `True` / `False`. PostgreSQL
  `\copy` parses these correctly; if you use a different loader, post-process
  to `TRUE` / `FALSE` literals.
